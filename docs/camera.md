# Camera configuration and verification

The default source is the official [LakeConroe.com ABC13 camera page](https://lakeconroe.com/live-web-cams-on-lake-conroe/live-web-cam-abc-13-news/). The backend periodically discovers a YouTube iframe from that page, rather than permanently assuming that video ID `UqrwUKSkMEE` remains current. If discovery fails, the configured URL is retained with an explicit limitation in `/api/camera`. Discovery confirms published configuration, not video playback.

The frontend uses YouTube's supported IFrame Player API: muted autoplay, inline playback, and supported control settings. YouTube branding, provider messages, embedding restrictions, and recommendations cannot be eliminated reliably or bypassed. `LIVE` appears only after the player emits `PLAYING`; buffering, stopped playback, API failures, and embedding failures remove that indicator. A playback watchdog and capped exponential retry reconnect only the camera, without reloading the dashboard. An optional alternative is attempted after a failure. The retry button restarts the primary camera.

Configure `camera.provider` as `youtube`, `image`, `iframe`, or `disabled`; set `camera.url`, `camera.source_page`, `camera.discover_from_source`, and optionally `camera.alternative_url`. Alternative YouTube sources and standard image extensions are detected automatically; other alternative URLs are treated as official embedded players. Use HTTP(S) URLs without credentials, and respect each provider's embedding terms. An arbitrary cross-origin iframe's playback cannot be verified: its indicator says `CAMERA`, never `LIVE`. Some sites block framing and cannot be used as an alternative. Image mode says `REFRESHED IMAGE`; its tooltip records when the image successfully loaded, which is not a claimed sensor/capture timestamp. Image URLs receive a cache-busting `_camera_refresh` query parameter, so avoid signed URLs that disallow additional parameters.

## Verification performed in the development environment

On October 20, 2026, requests to both the official camera page and the YouTube oEmbed endpoint for the known ID were denied by the cloud egress proxy (`403 Forbidden`, `httpx.ProxyError`). TLS verification remained enabled. Therefore the current published video ID, embedding permission, and actual live playback could not be independently verified in this environment. No stock image, fake camera stream, or simulated production imagery is substituted.

On the Raspberry Pi, allow HTTPS access to `lakeconroe.com`, `www.youtube.com`, the YouTube player/API assets, and the media hosts the official player requires (commonly `*.googlevideo.com`, `*.ytimg.com`). Test from the Pi's actual browser. The `/api/camera` endpoint exposes discovery limitations; the on-screen badge exposes actual player state. A successful oEmbed response alone would not prove live playback or embedding permission.
